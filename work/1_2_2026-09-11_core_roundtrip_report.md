## Результат

Проверены все **1131** файла в `data/fc_core_tests`, рекурсивно:

- **451** — исходный и сохранённый JSON совпадают (39,9%).
- **611** — модель загружена и сохранена, но JSON различается (54,0%).
- **66** — исключение при `FCModel.load()` (5,8%).
- **3** — исходный файл не является корректным JSON (0,3%).

Успешно записаны **1062** выходных файла. Ошибок на этапе сохранения нет.
SHA-256 всех 1131 исходников совпадает до и после прогона и при финальной проверке.
Библиотека, корпус и спецификация в рамках этой задачи не изменялись.

Полный реестр: [core_roundtrip_results.json](1_2_2026-09-11_core_roundtrip_results.json).
Каждая запись содержит имя файла, SHA-256, заголовок, статус и либо все
структурные расхождения, либо этап ошибки и traceback. Длинные строки представлены
префиксом, длиной и SHA-256; отсутствующий контейнер описан как одна разница.
При изменении длины массива сравнивается общая часть и фиксируются обе длины.

Выходные `.fc` сохранены в `/tmp/fc_core_roundtrip_2026-09-11/` с исходными именами.
Это временный каталог: после его очистки результаты можно воспроизвести командой ниже.

## Методика и воспроизведение

Использован Python 3.8.20 из `.venv`, исходный пакет `src/fc_model`, VERSION = 1.2.7.
Для каждого файла: строгий разбор входного JSON → `FCModel.load()` →
`model.save()` в отдельный файл → строгий разбор выходного JSON → рекурсивное сравнение.
Повторные ключи и NaN/Infinity запрещены.

Не учитываются порядок ключей JSON-объектов и лексическое оформление JSON
(отступы, пробелы, варианты экранирования строк). Учитываются порядок массивов,
наличие пустых полей, значения и типы: `true`, `1`, `1.0` различаются.
Base64 сравнивается как строка, без нормализации бинарных данных.
Порядок ключей не имеет значения на любой глубине. Пути различий — JSON Pointer;
в агрегатах `*` заменяет индекс массива. Агрегаты считают затронутые файлы,
поэтому их количества пересекаются и не должны суммироваться.

Независимая проверка через `json.dumps(..., sort_keys=True)` подтвердила
классификацию всех 1062 записанных файлов. Текущий `tests/test_round_trip.py`
использует более мягкий критерий с исключениями для пустых optional-полей;
этот компаратор в новом прогоне не используется.

Повторный запуск из корня проекта (выходной каталог должен быть новым):

```bash
PYTHONPATH=src .venv/bin/python work/core_roundtrip.py \
  --source data/fc_core_tests \
  --outputs /tmp/fc_core_roundtrip_next \
  --report work/1_2_2026-09-11_core_roundtrip_results_next.json
```

Код завершения 0 означает полное совпадение, 1 — расхождения/ошибки корпуса,
2 — ошибку параметров или отсутствие `.fc`. Скрипт продолжает работу после
исключения отдельного файла. Контрольные суммы позволяют заметить изменение
источников. Входной каталог защищён от записи результатов через параметры CLI.

## Основные наблюдения по сохранённым моделям

### Повторяющиеся ID property tables: 179 файлов

Во всех 179 случаях уменьшения длины `property_tables` во входе повторяются ID.
`FCModel.decode()` складывает записи в `Dict[int, FCPropertyTable]`; следующая
запись с тем же ID заменяет предыдущую. Изменения `type`, `properties` и `id`
при сравнении по позиции часто являются следствием этой потери, а не отдельной
конвертацией типа.

Пример: `Contact2dQuad4CGS4_01.fc` содержит `(id=1, type=6)` и `(id=1, type=5)`;
после сохранения остаётся только `(id=1, type=5)`. Это кандидат на разбор
идентификаторов и ссылок корпуса по решению пользователя. Автоматически
перенумеровывать ID без проверки ссылок нельзя.

### Поля оболочек из спецификации теряются

В строгом diff исчезают `direction_normal` (157 файлов), `thickness_change`
(45), `layers` (21). Эти поля явно описаны в основной схеме `property_tables`
в `docs/FC_INPUT_FORMAT.md`, но `FCPropertyTable.decode()/encode()` сохраняют
только `id`, `type`, `name`, `properties`, `additional_properties`.

Пример со слоями: `Contact2dMixed_Shell_Thermo_Tied_MPC.fc`.
Это установленное расхождение библиотеки со спецификацией; наличие этих полей
само по себе не основание считать файл устаревшим. Предлагается отдельное
исправление поддержки этих полей в библиотеке с тестами.

### Добавление полей и нормализация

- `additional_properties` добавляется в 372 файлах.
- `loads[*].dep_var_num` и `dep_var_size` добавляются в 42 файлах.
- Тип `loads[*].dependency_type[*]` изменяется в 54 файлах.
- В 101 файле все выявленные различия — только добавления полей.

Пример: `Beam21_HookDamp_VM76.fc` получает пустой `additional_properties`
и метаданные зависимостей нагрузок. Даже если это допустимая для решателя
нормализация, она не удовлетворяет запрошенному строгому критерию.

### Перестановка элементов сетки: 40 файлов

В 40 файлах меняются `mesh.elemids` и связанные бинарные массивы.
`FCMesh` группирует элементы по типу и при сохранении обходит группы.
Дополнительная проверка через публичный `FCValue` установила: во всех этих
40 случаях меняется порядок ID, а записи по ID (тип, блок, порядок, parent_id,
связность) совпадают. Это не разрешённая перестановка JSON-ключей, поэтому
строгий тест остаётся неуспешным.

Пример: `Contact2d_Quad4_LumpMass.fc`.

### Поля старых или неуточнённых схем

- `mesh.elem_materials`, `mesh.elem_properties` удаляются в 190 файлах каждое;
  `mesh.elem_coords` — в 136. В современной основной схеме mesh их нет.
- `restraint_sets` удаляется в 55 файлах, `load_sets` — в 35. Спецификация
  помечает эти секции как NOT USED в матрице совместимости.
- `bcs` удаляется в 49 файлах; соответствующей основной схемы в спецификации нет.
- `contacts` удаляется в 60 файлах. Матрица спецификации помечает его ACTIVE,
  но основная схема перечисляет только `contact_constraints`; библиотека
  не сохраняет `contacts`.

Для `contacts` требуется сначала решение пользователя или уточнение документа.
Для остальных полей отсутствие поддержки не доказывает, что их безопасно
удалять из теста: нужно проверить назначение и перенос данных в текущую схему.

## Ошибки загрузки: 66 файлов

Это группировка **первых** исключений, а не полный перечень дефектов файла:

- **22** — `AttributeError: 'str' object has no attribute 'get'` в
  `fc_materials.py:342`: группа материала представлена объектом, тогда как
  декодер ожидает список записей. Пример: `Beam21_HookDamp_CodeAsterSDLL100.fc`.
- **12** — `KeyError: 10` в `fc_conditions.py:195`, неизвестный код нагрузки.
  Пример: `Contact2dQuad4CGS4.fc`. Код отсутствует и в актуальной таблице
  `loads.type` спецификации; назначать замену без решения пользователя нельзя.
- **12** — Base64-декодер получает `list`; все 12 файлов имеют `header.binary=false`.
  Такой режим описан спецификацией, но текущий mesh-декодер ожидает Base64.
  Это ограничение библиотеки относительно спецификации.
- **7** — `KeyError: 'name'` в `fc_constraint.py:82`.
- **5** — `KeyError: 'elem_orders'` в `fc_mesh.py:68`.
- **4** — `KeyError: 'elem_blocks'` в `fc_mesh.py:67`.
- **1** — неизвестный код элемента 14 в `fc_mesh.py:86`.
- **1** — неизвестный код элемента 5 в `fc_mesh.py:86`.
- **1** — неизвестный код restraint-флага 8 в `fc_conditions.py:311`.
  Пример: `Contact3dHex20SplitedBeamAngularVelocity.fc`, `flag=[0,8,0]`;
  код 8 отсутствует в актуальной таблице `restraints.flag` спецификации.
- **1** — `dep_var_num shorter than data components` в `fc_conditions.py:310`.

Среди корректно разобранных JSON: 1119 файлов версии 3 (из них 12 небинарных),
5 версии 2 и 4 версии 1. Все 9 файлов версий 1/2 завершились ошибкой загрузки.
**Все 611 расхождений относятся к файлам, объявляющим версию 3.**
По одному заголовку нельзя определить актуальность всей структуры файла.

## Источники истины и следующие решения

Проверены `AGENTS.md`, `VERSION`, README, `FC_MODEL_LLM_CONTEXT.md`,
`FC_MODEL_API_INDEX_TLDR.md`, соответствующие схемы и legacy-разделы
`docs/FC_INPUT_FORMAT.md`, код load/save и доменных декодеров,
`tests/test_round_trip.py` и штатные unit-тесты.

Дополнительно обнаружены существующие расхождения документации:
LLM-контекст указывает 1.2.0 при VERSION=1.2.7; схема mesh описывает
`elem_types` как Base64 `[int]`, а библиотека декодирует по одному `uint8`
на элемент. Предлагается отдельно согласовать и синхронизировать эти места.

Разумный следующий этап: отдельно восстановить некорректные JSON; затем
разобрать повторы property table ID, подтверждённые пробелы библиотеки
(поля оболочек и небинарный режим), порядок сетки и legacy-секции.
В каждом случае сохраняется приоритет: **решение пользователя → спецификация →
библиотека → файл**. Этот отчёт не утверждает, что несовпавшие файлы deprecated,
и не проверяет запуск или результаты решателя Fidesys.
